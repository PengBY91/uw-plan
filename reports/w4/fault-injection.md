# W4-05 软件故障注入与 A0 反应

**结论：三类故障分开注入两个父数据（EuRoC V1_01、仿真条纹横梁 stripe_beam_v1_s01），共 20 份派生数据，加 2 次未注入故障的对照，全部按 1× 协议跑完 A0 并评分。** 在 V1_01 上：

- 相机短时掉帧（每段 ≤10 帧）几乎没有影响；
- 相机中断 3 s 出现短暂越限，中断 6 s 后误差不能恢复；
- IMU 中断 0.5 s 和 IMU 时间偏移 40 ms 都使 OpenVINS 发散到百米至公里级，但进程既没报错也没停止输出，相机槽覆盖率和对照完全相同；
- 偏移 5 ms 和 15 ms 时，OpenVINS 的在线时间偏移估计都收敛到了注入值。

在仿真条纹横梁上，IMU 中断 0.5 s 和偏移 5/15/40 ms 都没有可见影响。不过这条航段的对照本身已在四个轴上都越限（APE 0.386 m），相机故障的效应叠加在这个退化之上。两个父数据反应不同，至少有两个原因可能起作用：两套 OpenVINS 配置不同（见下），以及 EuRoC 无人机的动态远高于仿真 AUV；本报告没有逐项隔离。

**这些都是软件注入的故障，不代表浑水或任何真实水质条件**；真实水质下的对照要等 D 数据。

## 注入工具与派生数据

`scripts/data/inject_fault.py`：输入一个已通过审计的 ROS2 bag，输出新 bag 加 `fault.json`；原始数据只读。三类故障分开实验，每份派生数据只含一种故障：

| 故障 | 操作 | 改了哪个时间 |
| --- | --- | --- |
| dropout 短时掉帧 | 按种子在序列中间 80% 随机放 5 段，每段删 N 个连续双目对（cam0 和 cam1 成对删） | 只删消息；保留消息的 header.stamp 和 bag 记录（接收/回放）时间都不变 |
| offset 固定时间偏移 | 给 /imu0 每条消息的 header.stamp 统一加 Δt | 只改采样时间 header.stamp；bag 记录时间不变，所以回放节奏不变 |
| outage 消息中断 | 删掉某一路在 [60 s, 60 s + D) 内的所有消息 | 只删消息 |

时间偏移选择改 IMU 而不改相机，原因是这样 OpenVINS 输出的时间戳仍在相机时钟上，评分时不需要换算（相对偏移等价）。`fault.json` 记录：父 bag 每个文件的 SHA256、父数据审计、种子、区间（绝对 ns 和相对起点的秒数）、参数、改的是哪个时间、复制的话题，以及输出文件的 SHA256。写完后重新读取输出 bag，逐话题核对时间戳与预期完全一致、严格递增，不一致则以非零状态退出。工具测试见 `scripts/tests/test_inject_fault.py`，共 5 项：成对删帧、种子可复现、偏移只改 header 不改记录时间、中断窗口、拒绝覆盖和拒绝未通过审计的父数据。

派生 bag 只复制算法用到的三个话题（cam0、cam1、imu0），位于 `data/derived/fault/<父数据>_<故障>/`，原共 37 GB（清理后目录约 250 KB）。它们被运行记录引用；2026-10-13 清理时删除了 .mcap，保留 fault.json、metadata.yaml 和 `mcap-checksums.sha256`，可按同一种子和参数重新生成并对照校验和；按种子和参数可以重新生成。

强度设置：

- 掉帧：每段 2/5/10 帧，共 5 段，种子 1；
- IMU 偏移：+5/+15/+40 ms；
- 相机中断：1/3/6 s；
- IMU 中断：0.5 s，只做了一个强度，因为 V1 上这一档已经发散。

V1_01 的掉帧段起点为 18.6、68.1、73.1、101.1、124.1 s（相对 bag 起点）；仿真为 19.0、70.5、75.0、104.0、128.0 s。

## 运行设置

- 运行 ID 为 `fault_<v101|sbeam01>_<故障>_a0_r01`，对照为 `fault_v101_control_a0_r02` 和 `fault_sbeam01_control_a0_r01`。V1 对照的 r01 是脚本路径写错导致的失败记录，保留未删。
- 对照和故障运行用同一个 OpenVINS 构建（b64db17，另一会话的诊断版构建，只增加日志输出）和同一份代码提交（505c800）。
- 配置：V1 用 `configs/euroc_v101`；仿真用该数据集自己的 `openvins/` 配置。两者有关键差异：

  | 配置项 | EuRoC | 仿真 |
  | --- | --- | --- |
  | `calib_cam_timeoffset`（在线时间偏移） | true | false |
  | `calib_cam_intrinsics`（在线内参） | true | false |
  | `init_dyn_use`（动态初始化） | false | true |
  | `init_imu_thresh` | 1.5 | 0.1 |

- 每次运行都持锁执行，结束后做算法侧输入审计（`audit_input_trace.py`，对比派生 bag）和 `uwbench eval-traj`（对比父数据的真值）。全部 22 次运行的输入审计都显示：收到的消息与派生 bag 完全一致，没有回放丢样，所以下表的差异只来自注入的故障。

**偏移故障的评分问题。** OpenVINS 在线估计相机–IMU 时间偏移时，输出时间戳等于相机时刻加上估计的偏移，也就是落在 IMU 时钟上。实测输出相对相机时刻的偏移中位数分别为：

| 注入偏移 | 输出时间戳偏移中位数 |
| --- | --- |
| 对照 | 0.1 ms |
| +5 ms | 5.1 ms |
| +15 ms | 15.1 ms |
| +40 ms | 6.5 ms |

5 ms 和 15 ms 时，在线估计都收敛到了注入值；40 ms 时没有收敛，剩下约 33.5 ms 被状态吸收，最终发散。V1 的主参考（OpenVINS 修正版）是 20 Hz 的相机时刻序列，15 ms 的平移超出 10 ms 关联容差，所以只匹配上 11 个估计。为此另做了一套评分：参考换成 ETH 原始 200 Hz 真值（`manifests/euroc_v101_run_asl200.yaml`），估计时间戳减去注入的 Δt，换回真实时间（`eval-traj-asl200-timecorr/`）。结果如下：

| 运行 | 校正后 APE（m） |
| --- | --- |
| 对照 | 0.055 |
| +5 ms | 0.065 |
| +15 ms | 0.058 |
| +40 ms | 20627 |

原始 200 Hz 真值本身带有 OpenVINS 修正过的时间偏差，所以这套评分的绝对值高于主参考，只能用于同一套评分内部的相对比较。

**IMU 中断 0.5 s。** 删掉 100 个 IMU 样本后，OpenVINS 没有输出断档，也没有日志报错，但在中断后 15 s 内位置误差就达到 23 m，全程 APE 380 m。可能的原因是：EuRoC 无人机的加速度较大，跨 0.5 s 空档的传播误差无法被随后的视觉更新拉回，同时在线标定（内参、时间偏移）也一起被拖偏。本报告没有逐项隔离这些因素。

## OpenVINS 对各类故障的反应汇总

| 故障 | 输出 | 发散 | 恢复 | 逐轴 |
| --- | --- | --- | --- | --- |
| 相机掉帧 | 断档时长等于丢失时长加一个帧间隔；不报警 | 两个父数据都不发散 | 断档后立即恢复，V1 上看不出精度变化 | V1 仅在 5 帧档有 2.6 s 的 y 越限 |
| 相机中断 | 断档时长等于中断时长；中断期间没有任何输出（不是纯惯性外推） | 不发散，但误差留在恢复后的状态里 | 1 s 档可恢复；V1 上 3 s 档只短暂越限；6 s 档不恢复（没有回环，误差保留） | V1 上 z、y 受影响最大；仿真上沿梁 y 受影响最大 |
| IMU 中断 | **不断档**，持续输出 | V1 发散（百米级）；仿真不发散 | V1 不恢复 | V1 上三轴同时越限 |
| IMU 时间偏移 | 不断档 | V1 在 40 ms 时发散；5/15 ms 时在线估计收敛；仿真不受影响 | — | V1 在 5 ms 时有 2.8 s 的 y 越限 |

最危险的是 IMU 类故障：OpenVINS 在发散时既不断输出，也不报错，覆盖率指标和对照完全一样。也就是说，"有输出"不等于"正常"，这与 A 详案中"没有健康状态就不能评未报警风险"的要求一致。

## 局限

- 每种故障在每个父数据上只跑了 1 次，没有重复，种子只取了一个值。
- 仿真父数据的对照本身已严重越限，对相机故障的分辨力有限；下一步应换一条无越限的仿真航段（比如 Dam）作父数据。
- 两个父数据反应不同的原因（配置差异还是运动强度差异）没有隔离。可以用 V1 加关闭在线时间偏移的配置补一组对照。
- `benchmark` 子命令（P11 前半）没有实现，CLI 仍以非零状态退出；本轮用批处理脚本加各运行目录内的 run.json、input-audit.json 和 eval-traj 记录代替，汇总由 `scripts/experiments/summarize_fault_runs.py` 读取这些记录生成。
